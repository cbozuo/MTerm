Double Shift
全局搜索

两次 Shift，找到任何东西

在终端里，手离开键盘的成本远高于移动一次鼠标。我们把「找东西」做成一个 无入口感的动作：双击 Shift，面板在 16ms 内出现，五类本地数据已经就绪； 继续输入，结果在 8ms 内重排。它不是搜索框，而是 MTerm 的 全局命令层——找到会话就连，找到命令就发，找到设置就改，找到动作就执行。

01

设计判断

四个先于像素的决定。它们决定了这个浮层为什么这样长，而不是另一个「好看的搜索框」。

JUDGE 01零学习

键盘不是鼠标的备选

终端用户的手已经在键盘上。双击 Shift 不需要寻找按钮、不需要记快捷键、不会与任何 shell 输入冲突，是「零学习成本」的全局入口。

入口即肌肉记忆

JUDGE 02可执行

搜索不是跳转，是执行

结果不是「带我去某个页面」，而是直接完成动作：连接会话、发送命令、切换设置、运行动作。一次 Enter，搜索即操作。

Search → Act

JUDGE 03本地

一张本地索引，五类数据

启动时把会话、命令、设置、动作与标签页编织成一张扁平索引；按键即搜，搜索路径上没有 I/O、没有异步、没有网络。

1,284 items · in-memory

JUDGE 04硬预算

慢 16ms 就算卡

打开、输入、滚动都有明确预算。为守住 8ms，我们不做防抖、不做骨架屏、不做异步请求，也不接受任何「先转圈再出结果」。

16 / 8 / 60fps

一句话判断：如果用户需要「先想一下按什么」，这个功能就已经失败了。双击 Shift 的目标不是被发现，而是被条件反射地使用。

03

交互规格

触发器、输入法、键盘与执行语义，全部按「可落地」写死。这里的每一条都在原型中有对应实现。

双击 Shift · 时序状态机

只认「抬起后 80–360ms 内第二次按下」。不是双击速度越快越好，而是给手指一个自然的回弹区间。

面板已打开时再次双击 Shift 不重复打开；Esc 关闭后把焦点归还到打开前的元素。修饰键组合（Ctrl/Alt/Meta + Shift）不参与判定。

IME 兼容 · 污染键必须取消

中文输入法会向应用注入不可见的 Shift 编码，必须把它们与真实按键区分开，否则会出现「打字时突然弹出搜索」。

  • R1
    百度拼音左 Shift 会发送 U+0015，右 Shift 发送 U+0010；这两个码点不参与双击判定，并立即清空计时器。
  • R2
    部分 IME 在按键后尾随 U+0008（退格）。一旦检测到该字符，视为本次候选被污染，直接取消，而不是「再等第三击」。
  • R3
    输入框处于组合态（compositionstart 到 compositionend）时，任何 Shift 都不触发全局搜索；IME 候选窗打开时同理。

实现层面：只认 event.key === "Shift" 且 !event.repeat，同时拒绝 event.isComposing 与上述控制字符；这与 Slint 侧的 key event 过滤保持同一套规则。

// 触发器核心：只认干净的双击，任何污染都清零 let lastShift = 0; function onKeyDown(e) { if (e.key !== "Shift" || e.repeat || e.ctrlKey || e.altKey || e.metaKey) { lastShift = 0; return; } const now = performance.now(), gap = now - lastShift; if (lastShift && gap >= 80 && gap <= 360) { openPalette(); lastShift = 0; } else lastShift = now; }

性能与无卡顿

不是「优化到不卡」，而是把预算写进架构里。超过预算视为缺陷，不是体验问题。

打开首帧 P95Shift×2 抬起 → 面板与首屏结果可见，含遮罩合成
≤16msP95 / 120Hz 单帧
键入 → 列表更新5,000 条索引、中文输入法上屏后一次完成
≤8msP95 / keydown→paint 前
列表滚动固定行高 + 只渲染 40 行，不触发重排
60fps无掉帧 / 轨道合成
额外常驻内存索引 + 预计算小写串；不复制正文，不缓存 DOM
≤8MB相对空载
启动建索引1,284 条真实数据量级；与窗口首帧并行，不阻塞
≤30ms一次性 / 后台线程
怎么量出来的

打开：Performance.now() 在 keydown 落点打点，requestAnimationFrame 首帧回调再打点，差值写入 footer「上次打开」。键入：同一帧内完成过滤与 DOM 片段拼装，只替换 #palList 的 innerHTML。

压力测试把 6,000 条合成记录并入索引（总计约 6,842 项），同一个 web 查询仍走同步路径，实测值实时显示在 footer 与工具条。

三段式：把「慢」挡在用户之外

索引：启动时把会话/命令/设置/动作摊平成同一种 Footprint，预计算小写串与关键词，全部驻留内存。之后搜索不碰磁盘、不碰网络、不碰 SSH 会话。

查询：分词 + 分层评分 + 稳定排序，全同步；5k 条量级对 Rust 来说是一次内存遍历，对 JS 原型来说是 1ms 级的数组扫描。

渲染：只算可见窗口的 40 行，分类分组头单独计数；预览只在选中项变化时更新，60ms 淡入不改变面板尺寸。

① 建索引startup · 30ms

5 个 source 各自产出 SearchItem；统一字段、统一权重。会话含已打开标签，命令合并快捷命令与历史。

index.rs 只做写入与冻结，不做查询。

0.6ms
② 查询keystroke · 8ms

空白分词 → token AND → 分层评分（精确/前缀/词界/子串/子序列）→ 中英文与拼音别名 → 类别权重与最近使用加成 → 稳定 tie-break。

结果上限 40，All 每组 8 条。

③ 渲染paint · 4ms

列表只重建可见行；选中态只切 class；预览区 60ms 淡入；分类指示条 transform 140ms。

无骨架屏，无布局抖动。

NO.01
不做防抖

防抖的本质是「等用户停下来」。本地索引单次查询 <1ms，防抖只会让人感觉输入被吞。每次 input 都同步出结果。

NO.02
不做骨架屏

骨架屏是网络等待的遮羞布。这里没有网络请求，首帧就该有真结果；空态、无结果态都是确定的终点，不是加载中。

NO.03
不做异步请求

一旦搜索跨线程/跨进程，就要处理竞态、取消和乱序。索引留在 UI 线程的内存里，同步返回是最简单也最可控的架构。

为什么是 7 个文件，而不是一个大模块

搜索的四个关注点天然可拆：index 只负责「有什么」，query 只负责「怎么找」，rank 只负责「谁在前」，trigger 只负责「何时打开」。

拆开之后，单测可以逐个钉死：触发器不需要 UI，评分不需要真实索引，索引不需要键盘事件。
