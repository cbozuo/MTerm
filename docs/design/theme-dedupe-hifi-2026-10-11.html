唯一需要拍板的：老用户怎么办

改 DEFAULT_DARK/LIGHT 只对新用户生效 —— 老用户配置里已有 theme 字段，不会被覆盖。
建议：只让新用户默认门面，老用户保留自己已选的主题，不再做一次性迁移。理由是上一次 graphite 迁移用的理由是「新老用户一律用新底色」，前提是旧配色已不可用；而现在用户手里那套主题是他自己选的，替他改掉会直接毁掉「主题」这个设置的存在意义（而 §5 的整套改进恰恰是想让用户更敢用、更常换）。
如果坚持连老用户一起迁，需要在 config_file.rs 里把 graphite-* 也并进旧 id 重定向表 —— 代价是所有把 graphite 改成别的颜色相的老用户（比如选了 slate 后一直用着的）会被错误地拉回 graphite，需要按 ac 进一步区分，值得单独评估。

回到精简本身。分级依据是"下线后用户会不会察觉少了东西"。A 级是零感知缺失（本来就是同一套终端）；B 级是把差异让渡给"强调色预设"—— 强调色是三级设置，本来就能实时换色相，把 4 个只换色相的色相族收进预设，切换成本反而更低（换色相不需要重刷终端色表）。

存量配置：加 id 别名表，不要改用户文件

在 palettes::find 之前加一层规范化即可，一处生效、覆盖全部入口（启动读 config、set_theme、预览、单测）：

/// 历史 id → 现 id。别名只增不减：已下线套的旧 id 也留在这里，
/// 避免用户升级后静默丢主题（find 失败会静默回退默认档）。
pub fn canonical_id(id: &str) -> &str {
    match id {
        "islands-dark"  => "mterm-dark",
        "islands-light" => "mterm-light",
        // …此处并入 §2 下线 13 套的旧 id（含 tokyonight-dark / -light、
        //  以及 ayu-dark —— 它不是删干净，而是重定向到 ayu-mirage）
        _ => id,
    }
}
pub fn find(id: &str) -> Option<&'static Palette> {
    PALETTES.iter().find(|p| p.id == canonical_id(id))
}

别名表把改名和下线 10 套的迁移合并成同一件事 —— 这是上一轮 §2 里那两套 id 重定向表的同一张表。建议改名 + 下线一次性执行，中间态（改了名没建别名）恰好是唯一会出事的状态。

2.2 下线后：色相去哪了

收进强调色预设。切换强调色只改 3 个 UI 槽（ac / ac2 / dg_s），不重刷终端 ANSI —— 这正是"我想换个色相"的正确语义；换终端配色才该换主题。

上面这 4 个色相本来就已经在强调色预设里——「青 #00A2C7 / 靛紫 #5B5BD6 / 翡翠 #29A383 / 琥珀 #FFC53D」正是 palettes.rs:35-38 标注的 Radix 石板 / 藕荷 / 青苔 / 暖砂的 accent。也就是说色相从来没有丢，只是现在有了唯一正确的归属：下线这 8 套不会让任何一种色相从产品里消失。
唯一要顺手处理的是 ACCENT_PRESETS 里的 tomato = #E54D2E，注释写着「Radix 橄榄（已删族，色值仍为其 accent）」—— 一个指向不存在家族的预设。建议改名为「砖红 · 自定义」并把出处改成自定义，或直接移除。
