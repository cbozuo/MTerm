方案 A：字母用「文字色 + 小色点」，不用频道色
A prod-01 里字母取 text-secondary （暗 #b4b9c4 / 亮 #45454a，两档都 ≥ 9:1 ✓）， 字母右上角加一个 4px 频道色圆点。

方案 B：深浅两套频道色（推荐）
channel-color-dark / channel-color-light 参照 group-color-dark/light（theme.slint:244-255）的做法， 四槽各给深浅两个值，共 8 个。
优点：每档都能挑到达标值—— 暗色用提亮版、亮色用加深版，不再互相牵制。
这是唯一能根治的做法，代价只是多 4 个常量
但频道色还剩两个常驻显示点，不止字母
即便字母对比度不足，用户还有两条路看到频道： ① 点「同步」按钮打开管理对话框，双栏里有大色块 + 频道名； ② 状态条上的频道色方块（8px，对比度 5.15:1 ✓）。
所以字母不必独自扛——它是"扫一眼就知道"的快速通道， 不是唯一通道。建议做方案 B（深浅两套色），它成本极低 （4 个常量），且顺带把状态条色块也一起修正。
tab 紧贴：撤掉 1px 分隔线，左内边距收到 6px
v27~v33 的做法是「间隙归零 + 非选中 tab 右侧 1px 暗线」（画在 SingleTab 内部的 border-right，选中态 transparent）。 本轮把这条线整个撤掉，并顺手把左内边距 10px → 6px。
撤线的真实理由不是"更简洁"，是那条线在缩放下会变成间隙： 1px 暗线在 125% / 150% 缩放时被渲染成一道发丝缝，观感上就是 「tab 之间又有空隙了」——恰好是前几轮反复在修的那个症状。 它为了解决"两块粘成一片"，亲手造出了"两块之间有缝"。

块边界现在由谁承担
① 左缘分组色竖条（left: 0，3px）—— 每个 tab 的起点都有一根竖线，它本身就是边界标记， 比 1px 暗线更强（宽度 3px vs 1px，且是彩色）。

③ hover 底色：#2e323a，鼠标下的归属感。
唯一真会粘连的场景：相邻两个 tab 同组 + 无频道 + 都未选中，此时既无竖条色差也无底色差。 标题不 elide 时两段文字本身就把它们分开；真读不出来时 靠 hover 底色定位。
左内边距为什么能收
竖条 v32 起已 position: absolute; left: 0， 让位需求 = 3px 竖条 + 一点呼吸 = 6px。 原来的 10px 是在"必须有 1px 暗线、块边界要读得清"的前提下定的， 撤线后那份额外的呼吸没有存在理由。
有频道 / 无频道共用同一条规则： 无频道时首个 flex 子项自动变成标题，文字起点仍然对齐。
别给无频道单开一条 padding——那会让行内出现两种文字起点。
撤线的连带项（漏一个就会看出"漏了"）
① .tab.last 规则与 JS 里的 classList.toggle('last') 一起删——它只为"末 tab 不画线"存在，线没了就没有存在的理由。
② tab-width() 常数 64 → 59（省下的 5px 还给标题）。 必测不改常数的话，每个 tab 平白多 5px 空白， 该 elide 的名字不 elide。
③ 顶部 3px 横线的 parent.width 逻辑可以简化： tab 不再有边框，parent.width 就是视觉宽度， 不再需要"transparent border 不占视觉宽度"的补偿口径。
④ 拖拽插入位计算里的 if (i > 0) acc += 0 是分隔线时代的残留，一并删。
一条被否决的替代方案：把线换成更浅的灰
想过用 #3a3d46（亮于 tab 底）当分隔线，理由是"亮线在两种底色下都可见"。 否决：亮线读作"高亮分隔"而不是"分块"， 两个 tab 之间的关系从「相邻块」变成「被隔开」， 而 tab 行要表达的是同一组会话的平铺。
既然"块边界"这件事在 IDEA 里本来就不靠线解决（它连 gap 都不留， 靠选中态 + hover 区分），那就索性什么都不画—— 少一个要在深浅两档分别调色的变量，也少一个在缩放下变形的像素。

竖条贴各自的左缘、文字起点同一条垂线， 一行扫过去竖条连成一条线，文字起点也齐
根因：竖条是 flex 子项，跟着 padding 走
.gbar（width: 3px; flex: 0 0 3px）在 HorizontalLayout 里， 它的左缘 = tab 的 padding-left。 之前首 tab 特例 padding-left: 0（v11「首 tab 贴左缘」）， 其余是 10px → 竖条必然差 10px。
这不是竖条的问题，是首 tab 特例的副作用—— 特例是为了"贴边"，但没考虑到贴边会连带把竖条和文字一起拉走。
⚠️ v30 的解法不对，v32 已修正
v30 的做法是「取消首 tab padding-left: 0，全行统一 10px」—— 这让竖条对齐了，但竖条整体缩进在 tab 内 10px，不贴左边线。
正确解法是让竖条脱离 flex 流： position: absolute; left: 0，文字靠 padding-left 让开。
竖条标记的是「这个 tab 从哪开始」， 不是「文字从哪开始」——贴边才是它的语义。解耦后两者各归各的。
为什么不让首 tab 继续贴边
v11 定「首 tab 贴左缘」是为了消除"首 tab 缩进一截"的孤立感。
但那个孤立感已经被 gap: 0（v27/v28）解决了—— tab 之间紧贴之后，首 tab 不再"缩进"，它就是左边缘。
再叠加 padding-left: 0 只会让组内第一个成员与其他成员不同， 反而制造新的不一致。
两条已定规则叠加后的正确形态： tab 之间不留缝、tab 内部左内边距 6px
备选 B：竖条绝对定位（若你坚持首 tab 贴边）
把竖条从 flex 流里拿出来，absolute 定位到 x: 2px ——所有 tab 的竖条都贴各自的左缘。
代价：竖条与文字起点解耦， 首 tab 文字会比其余靠左一个内边距，换一种方式产生新的不一致。

「关闭频道」的语义必须写死，否则实现必然做错
你的定稿：关闭频道 = 只关闭"加入当前频道的所有活动会话"的通信， 不是关闭所有频道，也不是解散频道定义。

实现：一条 absolute 1px，铺满整宽
顶线不能画在 TabBar 组件里（它不知道状态条的存在）， 要画在状态条内部、y: -1px、left: 0; right: 0。
不需要 JS 计算——right: 0 由父盒宽度自动铺满， 所以切 tab / 拖拽 / 侧栏收放 / 窗口缩放都不必刷新顶线 （v23 那套 5 个刷新点可以全部删掉）。
净收益比 v23 少 4 个刷新点、少 2 个元素
v23 的五个刷新点：现在都不需要了
v23 分两段时要按选中 tab 量位置，因此需要 5 个刷新时机： 切 tab / 拖拽提交后 / 侧栏收放 / 窗口缩放 / 状态条从 display:none 恢复。
改成 right: 0 铺满后，这 5 处全部消失—— 顶线不再依赖 tab 位置，只依赖状态条自身的宽度。
额外收益：不只是少几行代码，而是 少了一类"忘了刷新导致错位"的 bug—— 这类 bug 最难查，因为触发时机很偏
分屏时的规则要定：状态条是一个 pane 一条（不是每 tab 一条）， 但顶线要断在本 pane 的活动 tab 下沿。多 pane 并排时， 两条状态条的顶线各自只在自己 pane 范围内断开——不能跨 pane 连成一条。 落地时顶线的 left/width 必须相对本 pane算， 不是相对窗口。

位置截图本项目改成
左栏标题 「分组 B 中的会话」下拉 「按分组筛选」。截图的写法会让人以为 「分组 B」=「频道 B」，而两者在本项目是两套独立身份

底部按钮 添加全部(D) / 全部删除(E) 改成 应用 / 取消（管理语义）+ 重置。理由见下方红框
中间 只有底部 +/- 加双击直达：左栏双击 = 加入， 右栏双击 = 移出。底部按钮保留但降为辅助
为什么不用「确定 / 取消」
截图那两个按钮意味着「成员表立刻生效」。但本项目当前 app.rs:7971 是无差别全量广播—— for (target_id, handle) in h.iter() 遍历所有在线会话， 连发送方自己都发，既没有成员表也没有频道概念。

所以这个对话框是「模型改造的入口」不是「已有功能的配置界面」： 点「应用」要同时做三件事——
① 写成员表 tab_id → channel；
② 把 send_raw 的全推改成按当前 tab 所在频道筛选；
③ 排除发送方自己（现状会发给自己，靠 interactive_echo_until 压回显，属于将错就错）。
工作量全在 Rust 侧slint 侧只是多一个对话框。
四槽是固定的，不能增删 顶部四页签永远显示全部 4 个，即使某频道 0 成员也保留（显示 0）。
不能像 DBeaver 那样「新建频道」—— 频道要参与输入定向，槽位必须稳定可预期；而且色板是固定四色， 新增槽就要扩色板，会与分组色 24 色混淆。
一个 tab 只能属于一个频道 已在其它频道的会话在左栏置灰并标注，不能直接加入—— 要先从原频道移出。防止出现「同时收 A 和 B 两路输入」的歧义。
实现置灰行不可点，但仍显示原因 （悬停出 tooltip「已连接其它频道，先移出」）。
本窗口固定在成员里且不可移出 当前窗口的 tab 恒在当前频道（否则自己发给自己没意义）， 标记「本窗口」并禁用其移出。否则用户会困惑 「为什么这个移不掉」。
「重置」是必要的，不是多余 四个频道的成员表会持久化，一旦存错用户很难自己看出来。 「重置」= 回到「每频道仅本窗口」的默认态， 而不是清空——清空会让所有输入无处可去。
离线会话要不要列出来：截图只列在线的。本项目建议列出全部会话， 离线的那几个置灰并标「离线」——因为成员表是持久化的， 临时下线的机器回来后应该自动恢复同步；若不列出，用户得先把机器连上才能配， 绕路。落地时 Rust 侧过滤 handles 之外还要读 ConfigStore.sessions()。

顶栏按钮改三态后可这样验收 ① 未加入 → 按钮灰，点开对话框停在空槽频道；
② 已加入 X → 按钮亮，点开时页签预选 X；
③ 已暂停 → 按钮亮但带暖色，点它先恢复再开对话框。
演示稿本轮只做了 ①②， ③「暂停」在主界面的频道状态条上。
快捷键：先只做两个 Ctrl+Shift+S 打开对话框、Enter 应用、 Esc 取消。
别学截图标 (D)/(E)「添加全部/全部删除」—— 那是 DBeaver 的，本项目左栏可能几十个会话， 「全部加入」几乎永远不是用户想要的，误点代价还很高。 要批量就配合分组筛选（先筛分组、再全选该组）。
三个状态在左栏里同屏可见 可加入（正常）／已在其它频道（置灰 + 原因）／离线（置灰 + 标注）。
不要用 tooltip 独占原因——用户是在扫列表， 置灰行要能一眼看出为什么不能点，否则会反复点。
切页签不丢选择 四个频道的成员表在对话框内是暂存态，切来切去不会丢。 只有「应用」才写回、「取消」才丢弃——不能改一下就立刻生效， 否则误点无法撤销。
入口与状态条要联动，不能各管一套
顶栏「同步」按钮（app.slint:1718-1721）现在是 二态 toggle（开 = 广播中）。改成频道模型后它应该是三级： 未加入任何频道（点击 = 打开本对话框）／ 已加入频道 X（点击 = 打开本对话框，当前页签预选 X）／ 已暂停（点击 = 恢复发送）。
不能保留二态——「开」这个状态在新模型里已经不存在了： 输入是否广播，取决于「当前 tab 在不在某个频道里」，而不是一个全局开关。
