02重构判断：一个组件、两个宿主、一条有结构的数据

三条判断决定了后面所有细节。每条都先说「不这么做会怎样」，再说选它。

① 形态：不是下拉，是「向上展开的检索面板」

老实现是个 300px 宽的窄下拉（只有「文本 + 类型」两列）。它装不下这次要的三样东西： 搜索框、过滤胶囊、行内动作。而历史面板和四段式提示框的性质不同 —— 提示框是「我正在补什么」， 面板是「我以前干过什么」，后者本质是个检索界面，所以按 560×386 的面板做，向上展开、 右边缘对齐命令栏内距。

② 结构：四段，但第二段是「列表」，第三段是「页脚」——没有详情区

四段式提示框有 94px 详情区（语法签名 + 说明），因为命令需要解释。历史条目不需要解释，它需要「看清全文」 —— 长命令（journalctl -u nginx -n 100 --no-pager）在 560 宽里必然被省略号截断。 所以这里用悬停全文卡（复用「发送命令」窗已有的 .cmdpop 机制）， 而不是固定详情区：不占高度、不推动布局、鼠标不动就不用看见它。

③ 数据：从 Vec<String> 升到 Vec<HistoryEntry>

现在config_file.rs:449
/// Recent commands sent from the command box,
/// oldest first, capped (#55).
pub command_history: Vec<String>,

// 去重靠 retain + push（config.rs:1913）
// 上限 CAP = 200
// 顺序 = 最旧在前（↑ 回溯要这个顺序）
缺：时间（无法排序/分组/显示「2 小时前」）、频次（无法做「常用」）、置顶。
提案defaults_rev 10
pub struct HistoryEntry {
  pub cmd: String,
  pub last_used: i64,   // unix 秒
  pub uses: u32,        // 去重命中 +1
  pub pinned: bool,
}

// 旧字段保留一个版本，只读不写
// （rev 10 迁移时读它、写进新字段）
顺序仍存「最旧在前」。但这已经就是「最近使用序」 —— 因为 push_command_history 每次把该命令 retain + push 移到末尾 （config.rs:1919），末元素恒为最近使用。所以面板的「新→旧」显示 就是把这根轴反过来，不需要排序算法。
先纠正一个常见误解：上一版稿子写「存储顺序 = ↑ 回溯语义，显示顺序 = 检索语义，两者不共用一根轴」—— 这句话是错的。回溯轴本身就是 recency 轴：config.rs:1913-1926 的 retain + push 让「最近用过」永远在末尾，所以 ↑ 从末尾往回走， 走到的正是「越来越久以前」。两根轴是同一根，只是方向相反。

这个事实把「排序」这件事的代价降到了最低：默认档不需要排序，.iter().rev() 即可。 真正需要排序的只有「常用」档（按次数）。
硬规则：默认档禁止按 last_used 排序，必须反转存储序（这条在原型里真实踩过）。

乍一看「按最近使用排」=「按 last_used 降序排序」，两者是同一件事 —— 不是。 时间戳有精度上限，并列必然发生：
· 原型里 ago 是整数分钟 —— 连续执行 3 条命令后它们全是 ago=0， 稳定排序遇并列会保持数组顺序，而数组是存储序（最旧在前），于是最早执行的那条排第一， 和用户预期正好相反；
· 真实实现里 last_used 是 unix 秒 —— 同一秒内连发多条（脚本、补全回车）照样撞车。

而存储序没有这个问题：push_command_history 每次「摘掉 + push 到末尾」， 「谁最新」在数组位置里是精确的、无并列的。所以正确的实现是 先过滤、再 reverse()（Rust 侧 .iter().rev()）； 只有「常用」档（按次数，真有并列需求）才写比较器，且破平键用存储位置而不是时间戳。

排序规则：四档，两个维度不混

过滤回答「看哪些」，排序回答「按什么排」，是两个独立维度。所以工具栏上它们是两组控件， 不挤在一排胶囊里。过滤有三档（改变集合），排序有两档（改变顺序）。

一个必须写下来的前提：执行完要回写历史。 面板里执行一条命令之后，必须走一次 push_command_history（config.rs:1913）： 次数 +1、last_used 刷新、该条摘掉后 push 到存储末尾。少这一步， 「最近使用优先」就失效了 —— 用户执行完再打开面板，那条还停在原地， 看起来就像排序坏了。

命令栏里敲一条没执行过的命令也一样要进历史（uses = 1）， 所以这条逻辑有两个分支，不是「只更新已有的」。

这也是沙盘上一版的真实失真：doRun() 只往终端写回显、没回写历史， 于是「次数」不涨、时间不归零、条目不动 —— 排序规则本身是对的，但看不到它生效。

「次数」不是排序键 —— 视觉权重必须说清这件事

默认档按时间排，但列表右侧同时显示「7 次 · 4 分钟前」两列。如果两列一样亮， 用户会自然地拿「次数」去核对顺序，然后发现「12、9、6、7、4」是乱的 —— 这是显示层制造出来的误读，不是排序错。

排序档「N 次」的视觉「时间」的视觉
最近（默认）7 次常规 text-muted —— 它是排序键，读起来最自然
常用12 次（accent + 加粗）压暗到 .6 —— 退为次要信息

这是高保真的表达力：同一个界面，切换排序时让「谁是排序键」在视觉上直接可读， 用户不需要去回忆刚才点了哪个按钮。实现上只是给 .pb-list 挂一个 by-freq 类，切换两段的 color/opacity。

不做字母序。面板是「回忆我敲过什么」，不是「查字典」；而且「按名字找」已经由搜索框承担 （键入即过滤，实时命中高亮）。再加一档字母序，等于给同一个意图两条路径，还要让用户选。

置顶不参与排序 —— 这一条容易做错。如果置顶项被强行提到最前，「最近用过的那条」就不在第 1 行了， 而用户 Ctrl+R 十次有九次是来找刚敲过的那条。置顶的价值是 标记 + 单独一档 + 不被 CAP 200 淘汰，不是插队。 淘汰规则要跟着改：config.rs:1920-1925 现在是 drain(0..len-CAP)（直接砍最旧的）， 必须改成「从队首找第一个非置顶的删」—— 否则置顶项会被后续执行悄悄挤掉。
实现时顺带修掉两处现存矛盾（本次重构的附带收益）：
① 显示序：CHANGELOG #331 定的「从新到旧显示」在代码里从未实现 —— terminal_ui.rs:198 的 history_view_rows 原样返回存储序（最旧在前）。 面板要新→旧，得在视图层反转，别再去改存储序（会砸掉 ↑ 回溯）。
② 默认选中：terminal_view.slint:1393 取 length-1（因为列表最旧在前）， 而 :2511 取 0。新方案下列表是新→旧，默认选中一律是 0 —— 一个数，不用再写「取最后一个」这种反直觉补丁。

⑤ 两处宿主：命令栏浮层 + 发送命令窗左栏

send_cmd_window.slint:455-505 的「最近」和命令栏面板是同一件事。抽成组件后， 发送窗白拿搜索、置顶、删除、全文卡；命令栏白拿「插入到光标处」的能力（发送窗已有）。 这是 command_hint.slint 已经验证过的做法 —— 那次抽组件就是为了「别再长出第二份实现」。 两处共用组件时，排序规则也共用（§2 ④ 的四档）—— 同一个用户在两处看到不同的顺序会以为数据有问题。

06键盘契约：搜索框持焦，方向键照样能用

这是整套交互最容易做错的一处。历史面板一旦把焦点交给搜索框，↑↓ 就被 TextInput 吃掉（光标在文本里移动）—— 用户会以为「选中项坏了」。 解法是在搜索框的 key-pressed 里先拦方向键，而不是另设一个「列表焦点态」。 这样只有一个焦点、一套键位、没有模式切换。

按键面板打开时边界 / 说明
↑ / ↓移动选中项（在可见行内循环）选中项只能在画出来的行里循环 —— 数据 42 条、只画 8 行，用 rows.length 取模会选到屏幕外的一条（四段式稿里踩过）。
Home / End首 / 末条列表是新→旧（§2 ④），所以 Home = 最近用过的那条（默认选中项），End = 最久远的那条。列表很长时的快速跳转。
PgUp / PgDn± 一屏（8 行）夹在 [0, len-1]，不循环。
↵执行选中项先关面板再发键（§5）。空态时 ↵ 不做事，不放行给命令栏 —— 避免「在面板里回车把半截命令发出去了」。
Tab填入命令栏，不执行，并关面板填完把光标放末尾。与「命令栏 ↑ 回溯」同一个结果，只是这条更明确。
Del删除选中项 + 弹撤销只在搜索框为空时接管；搜索框有字时 Del 必须是「删掉光标右边那个字符」—— 这是最容易误伤的一处。
Ctrl+Z撤销上一次删除与系统撤销语义一致；没有可撤销项时放行。
Esc关面板（搜索框有字时先清搜索）两段式：第一次清空搜索，第二次关闭。这是所有检索界面的通行手感，也避免「打了半天字，一按 Esc 全没了」。
直接打字进搜索框并过滤因为搜索框默认持焦，不需要额外处理；如果将来焦点跑掉（比如点了行），key-pressed 在面板层兜底把可打印字符塞回搜索框。

点面板外关闭遮罩层必须真的存在且只盖到命令栏上沿；今天那层 2000px 的隐形遮罩是 bug 源头，新实现要绑到面板可见性上（open 而不是 hist-popup-visible）。
为什么不做「两个焦点区」（搜索框一个、列表一个，Tab 切换）：那套模式需要用户先理解 「我现在在哪个区」，而且 Tab 已经被「填入命令栏」占用了。Raycast / VS Code 命令面板 都选了「单焦点 + 方向键拦截」，这是同一个理由。

07四个争议点：选了什么、不选什么、为什么

这几条都会推翻或修改既有决策，所以单独列出来。实现时如果只记得结论、不记得理由，很容易「优化」回去。

01搜索框放顶部（推翻 #131）
选顶部，与过滤胶囊同一行，构成一条工具栏。
不选底部（#131 的定案：「原先在顶部、位置随历史条数上下浮动、不好找」）。
理由#131 的病根是面板高度随内容变，不是搜索框的位置。这次高度锁死（§4），搜索框放顶部也不会漂。而顶部搜索 + 过滤是一整套「检索界面」的心智模型，底部会让人以为是「输入命令的地方」。
回归search_field_sits_above_the_list：采样搜索框边框 y 必须小于首行 y。
02行内动作键，不做右键菜单
选悬停/选中时右侧浮出 ▶ ⧉ ⌫ 三个 24px 键。
不选右键菜单（命令栏的快捷命令已经占了右键，且不可发现）。
理由历史面板的核心动作只有三个，且都是「对单条」的。三个图标键的发现成本远低于右键；用绝对定位 + 元信息淡出，不推动文字（否则悬停时整行文字会横跳）。
回归hover_actions_do_not_shift_the_command_text：悬停前后命令文本 x 不变。
03删除可撤销，不做二次确认
选立即删除 + 5s 撤销浮条（单条撤销栈）。
不选确认对话框（打断、且删除是高频微操作）；也不选「批量恢复」（会把面板变成命令管理器）。
理由误删一条历史是低频、低损失、可重放的操作 —— 用户重敲一次就回来了。为它弹模态框的代价远大于收益。但「立刻落盘不可恢复」（今天的实现）也不可接受，撤销是最小代价的兜底。
回归delete_shows_undo_toast_and_restores_on_undo。
04置顶不改列表顺序
选置顶项在「全部」里保持原位置，只多一枚图钉；「置顶」过滤里才只列它们。
不选置顶项强制排到最前。
理由强制置顶会让「最新一条」不再是最上面那条 —— 而 Ctrl+R 十次有九次是找刚敲过的那条。顺序一变，肌肉记忆全废。想要「常用的」有「常用」排序档，想要「固定的」有「置顶」过滤档。
回归pinning_does_not_reorder_the_all_view。
05排序与过滤分成两组控件
选工具栏右侧两组：过滤胶囊（全部/置顶/今天）+ 排序分段（最近/常用）。
不选把「常用」「今天」混在同一排胶囊里，当成同一维度。
理由过滤回答「看哪些」，排序回答「按什么排」b>。混在一排，用户点「常用」时不知道会改变集合还是改变顺序 —— 而这两件事的视觉结果完全不同（一个是少了行，一个是行换了位置）。
回归视觉分组：两组控件之间有可见间隔/底色差，不是同一排胶囊。
06默认排序 = 最近使用，不做字母序
选默认「最近」；因为存储序本身就是 recency 序，默认档根本不需要排序（.iter().rev()）。
不选字母序；也不做「按最后使用时间」以外的任何默认排序。
理由面板是「回忆我敲过什么」，不是「查字典」；「按名字找」已经由搜索框承担（键入即过滤、实时高亮）。再加字母序等于给同一意图两条路径，还要让用户选。
更实际的理由：push_command_history 每次 retain+push 移到末尾，存储序 = recency 序，所以默认档零成本 —— 而字母序要额外排一次。
回归default_order_is_most_recent_first：首行 = 最近使用的那条。

← → Tab在「取消 / 清空」之间切换焦点只有两个键，来回切即可。
↵等价于「点一下确认键」，但不会一步清空抄项目里的一条明文规定： confirm_dialog.slint:43-45 —— destructive confirmations must not become keyboard-confirmable merely because they share this component。 回车是最容易误触的键（手还停在输入上），破坏性操作不能靠它确认。
其他任何键吞掉不能让字符穿透到搜索框去改过滤词 —— 那会让用户以为「确认层消失回列表了」。

④ 置顶保护：清空不删置顶项

这是本次唯一一个「技术上可以不做、但做了才讲得通」的决定。

置顶 = 用户明确说过「这条我要长期留着」。清空时把它一起删掉， 等于把用户刚表达过的意图反着执行一遍 —— 而且他很可能就是因为知道会被清掉，才专门去置顶的。

这也和 CAP 淘汰的规则对齐：置顶项永不被自动移除（§2 已定，config.rs 的 drain(0..len-CAP) 要改成「从队首找第一个非置顶的删」）。清空是同一个语义的极端情形。

确认层文案必须把这件事说出来并给出精确数字：「将删除 40 条记录 · 无法撤销 / 这 2 条置顶命令会保留」。如果一条置顶都没有，就顺势教一手：「（置顶的命令可以保留）」。
排版踩坑记录（第一版做成左对齐，被截图打回）

初版给 .pb-confirm 写了 flex-direction:column; justify-content:center; padding:0 20px —— 我以为这样就「居中」了。实际渲染出来是：三块内容全贴在左上角， 右侧甩出三分之二宽度的空白，读起来像页面加载到一半。

根因：justify-content 只管主轴（这里因为是 column，主轴是竖向）， 所以它把三块内容在竖直方向居中了；但横向（交叉轴）没设 align-items， 子项默认 stretch，而块级文字又从左边开始排 —— 于是每一行都左对齐、 且宽度撑满，中间那个「居中」的错觉完全不存在。

修法三件套：
① align-items:center —— 补上交叉轴居中（这才是「横向居中」）；
② text-align:center —— 多行文字在各自的块内也居中；
③ 文案从「一句长句」拆成三行短句 —— 居中排版的宽容度远低于左对齐： 左对齐时句子长一点只是行宽变大，居中时一行太长会显得头重脚轻。 拆成「标题 / 主行（删几条）/ 副行（置顶保留）」之后，三行都是 12~16 个字符， 视觉上正好组成一个居中的方块。

顺带修掉的第二处：页脚原本一直挂着 ↑↓ 选择 / ↵ 执行 / Tab 填入 / Del 删除， 但这些键在确认态下全部失效。用户会去按 Del 以为能取消 —— 这是实打实的误导。 现在整行换契约（见上方第 ⑥ 条）。

⑦ 想过但没做的三件事

方案结论为什么

一句话总结：先把「点 🕘 什么都不发生、还白吃一次点击」这个 bug 认下来（面板绘制代码已丢）， 然后按一个组件（history_panel.slint）、两个宿主（命令栏 / 发送窗）、一条有结构的数据 （HistoryEntry + rev 10 迁移）重建：56 高的工具栏 + 锁 3–8 行的列表 + 28 页脚 + 可撤销删除， 键盘单焦点、搜索框持焦、方向键拦截；唯一不可逆的清空走面板内确认层 + 二次解锁 + 置顶保护。 这份稿子可以直接作为 tests/history_panel.rs 的验收基准。
