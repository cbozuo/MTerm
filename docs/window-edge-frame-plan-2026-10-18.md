# 主窗口「细线与边界不贴合」—— 根因分析 + 方案 A 对照实验结果 + 修复清单

> 日期：2026-10-18（01:30 实验 / 02:0x 落地）
> 状态：**已按「修正后的方案 B」落地并真机验证**（详见 §8）。方案 A 对照实验的结论保留在 §0。
> 现象（用户原话）：软件主界面周围的细线与边界并没有真正的重叠贴合。

---

## 0. 实验结论（TL;DR）

用临时构建跑了一次方案 A（让 DWM 系统边框变成唯一外框，主题色 `#4E5157`），200% DPI、1500×900 窗口实测：

| 项目 | 实测结果 |
|---|---|
| `DwmSetWindowAttribute(DWMWA_BORDER_COLOR)` | **S_OK（hr=0x0）**，颜色精确生效（取到 (78,81,87) = `border-strong`） |
| 系统边框位置 | **正好在窗口真实边界上**：窗口最外一圈像素就是边框色，内容紧随其后，没有内容环、没有非客户区偏移（`client rect == window rect`，DWM 扩展边界 == 窗口矩形） |
| 系统边框粗细 | 四条边、各 5 个采样点全部 **2 物理像素**（200% 下 = 1 DIP），不是 1 设备像素 |
| 系统圆角 | 拟合圆：圆心 ≈ (16.5,16.5) 物理，半径 ≈ **16.1~16.3 物理 = 8 DIP** |

**结论：方案 A 能 100% 解决"线与边界不重合"（它画的就是边界），但代价是最外框在 200% 下是 2 物理像素——是主界面其它 hairline（1 设备像素）的两倍粗，与项目既定的「1 设备像素」线宽语言冲突。**

同时实验暴露出一个**更严重、之前被误判的根因**（见 §2）：

> **Win11 的 DWM 圆角半径是 8 DIP（随 DPI 缩放），不是代码注释里假定的「固定 8 物理像素」。**
> 200% 下真实裁剪半径 = **16 物理像素**，而当前自绘弧按 8 物理像素设计 → 四角弧实际上**整段落在窗口裁剪区之外，被 DWM 裁掉了**；直边也在离角约 10 物理像素处被裁剪弧切断。
> 即：现在**四角根本没有边框线**，直边也接不到圆角——这比"内缩 1 像素"显眼得多，是「细线与边界没有重叠贴合」的主因。

## 1. 证据

### 1.1 直边：恒定 1 设备像素缝（代码事实，未变）

`ui/app.slint:9185-9321`（`if root.custom-titlebar && !root.window-maximized` 内的 `#win-edge-frame`）：

| 边 | 当前位置（行 9250-9276） | 换算到物理像素 | 结果 |
|---|---|---|---|
| 上 | `y: Theme.hairline()`，高 `hairline()` | 占第 **1** 行 | 第 0 行留内容 |
| 左 | `x: Theme.hairline()` | 占第 **1** 列 | 第 0 列留内容 |
| 下 | `y: win-h - 2*hairline()` | 占第 **H-2** 行 | 第 H-1 行留内容 |
| 右 | `x: win-w - 2*hairline()` | 占第 **W-2** 列 | 第 W-1 列留内容 |

`hairline() = 1px / device-pixel-ratio`（`ui/theme.slint:490-492`）→ 线本身粗细、设备像素对齐都没问题，问题只是**整体内缩了 1 个设备像素**（r2/r3/r4 注释写明是故意的，怕被裁剪弧 AA 削掉）。

### 1.2 四角弧：半径假设错了（本轮实测纠正）

- 当前实现：`Theme.radius-win = 8px / device-pixel-ratio`（`ui/theme.slint:463`），注释断言"Win11 DWM 圆角固定 8 **物理**像素、不随 DPI 缩放"（r1 注释）。
- **本轮实测（200% DPI，系统边框染色后量窗口外缘）**：圆角圆心距窗角 ≈16.5 物理、半径 ≈16.1~16.3 物理 → **8 DIP**（`8 × 2 = 16 物理`）。圆的切点也在约 16 物理像素处才收进直边。
  → 结论：**半径是 8 DIP，随 DPI 缩放**。之前"固定 8 物理"的结论是错的（应该在 100% 下量过、把 8 物理与 8 DIP 混为一谈了）。
- 叠加 Slint `Path` 的 fit 变换（`i-slint-core 1.18 items/path.rs::fitted_path_events`：`bounds = 元素尺寸 − stroke-width`、`offset = stroke-width/2`，渲染器 `translate(offset)` 后再画），200% 下当前四角弧实际渲染为：
  - 圆心 (7.5, 7.5) 物理、中心线半径 5.69 物理、外缘半径 6.19 物理；
  - 而窗口裁剪圆：圆心 (16,16) 物理、半径 16 物理；
  - 弧上最靠角的一点 (3.12,3.12) 到裁剪圆心距离 = 18.2 > 16 → **在窗口外，被裁掉**；弧顶 (7.5,1.31) 距离 = 16.97 > 16 → 也被裁掉。
  - 直边同样被裁剪弧切断：上边（第 1 物理行）在 x ≈ 10.4 物理之前就被裁掉。
  → **现状：四个角没有线，直边在角前 ~10 物理像素处消失。**
- 因此用户看到的"细线"和"边界"在四角完全不是同一条曲线；在 100% DPI 下（裁剪半径 8 物理）这个错误只有 1~2 像素级，不太明显——**200% 屏把它放大到 ~10 像素**，所以现在才被看到。

### 1.3 直边缝的可见性

10-17 新增 `Theme.zone-backdrop`（窗口背板 = root 再压暗 32%，`#161619 → ≈#0F1011`）+ 四分区半透明，使最外 1 设备像素的内容环变成近黑色，与 `border-strong #4E5157` 反差拉大——直边那条 1 像素缝因此更明显。

### 1.4 实验截图（200%，1500×900 窗口，缩放 12×）

- `target/exp-edge/out/sysonly-edge-top.png`：桌面 → **2 物理像素边框** → 内容，边框外缘就是窗口边界。
- `target/exp-edge/out/sysonly-corner-tl.png`：DWM 画的外框圆角，半径约 16 物理（8 DIP），线与边界完全重合。

## 2. 根因（更新版）

1. **四角（主因）**：`radius-win` 把 DWM 圆角当"固定 8 物理像素"（`8px / dpr`），实际是 **8 DIP**。200% 下自绘弧半径只有应有的约 1/2.4，且被 Slint Path 的 fit 再缩一次 → 整段弧落到窗口裁剪区外被裁掉，四角无线；直边也被裁剪弧切断。
2. **直边（次因）**：整圈直边主动内缩 1 设备像素 → 线外恒有 1 设备像素内容环。
3. **Path fit 未计入**：即使半径改对，按"1 单位 = 1 物理像素"写坐标仍会整体偏内（`bounds` 减 stroke、再 `translate(stroke/2)`），端点接不上直边。

## 3. 方案

### 方案 A（已实验：对齐完美，但线宽 = 1 DIP）

- 做法：`DWMWA_BORDER_COLOR` 设为主题 `border-strong`，删掉自绘框。
- 实测优点：线与边界完全重合（系统画的就是边界）；圆角由 DWM 保证；颜色可精确跟主题；代码净减 ~100 行；窗口 client/window 矩形无偏移，不影响布局。
- 实测缺点：**200% 下 2 物理像素**（1 DIP），比其它 hairline 粗一倍；且 125% / 150% 下会落在 1~2 物理像素之间（DIP 缩放）。
- 如果用户接受"外框比内部细线粗一档"，这是最省、最稳的方案；否则走 B。

### 方案 B（推荐：1 设备像素 + 真正贴边，已按新实测修正）

1. **修半径**：`Theme.radius-win: 8px`（去掉 `/ device-pixel-ratio`）。这同时修好 `BrandLogoBtn`（左上角 hover 高亮）与 `WinBtn` 关闭键（右上角）的圆角——它们也读 `radius-win`，现在在 200% 下同样偏小一半。
2. **直边贴真实边界**（填充矩形，整设备像素）：
   - 上 `x:0, y:0, w:win-w, h:hairline`；下 `y: win-h - hairline`；左 `x:0`；右 `x: win-w - hairline`。
3. **四角用描边 Path 精确压在裁剪弧上**（Slint 侧即可，不需要 Rust 动态几何）：
   - 命令用固定的"半径 = R、圆心 =(R,R)（单位）"的 90° 弧（R 取 8，即 `radius-win` 的数值）；
   - 元素尺寸 `R × R` 逻辑像素、`x/y = 0`；
   - **viewbox 用动态值抵消 Path fit 的缩进**：设 `h = Theme.hairline()`（逻辑长度），则
     ```
     viewbox = 2R(R − h) / (2R − h)
     ```
     推导：fit 后 scale=(R−h)/viewbox、offset=h/2 ⇒ 渲染半径 = R·scale = R − h/2、圆心 = h/2 + R·scale = R（正好是裁剪圆心）；于是**外缘 = R = 裁剪弧**、厚度 = h = 1 设备像素、内缘 = R − h。
     实际值：200%（h=0.5 逻辑）→ viewbox ≈ 7.742；100%（h=1）→ ≈7.467。
   - 四条命令（TL/TR/BR/BL，元素各自贴在对应窗角，单位坐标系）：
     ```slint
     "M 0 8 A 8 8 0 0 1 8 0"    // TL
     "M 0 0 A 8 8 0 0 1 8 8"    // TR
     "M 8 0 A 8 8 0 0 1 0 8"    // BR
     "M 8 8 A 8 8 0 0 1 0 0"    // BL
     ```
     （`stroke: Theme.border-strong; stroke-width: Theme.hairline(); fill: transparent; clip: false;`）
   - 数学上，弧端点会精确落在直边的中心线上（上边 y=0.5 物理、x=16 物理），切点处无缝衔接。
4. **只在 DWM 圆角真正生效时画弧**：Rust 把 `DWMWA_WINDOW_CORNER_PREFERENCE` 的返回值（S_OK）回写成 AppWindow 的 `win-rounded`；Win10 / 失败 → 只画直角直边（窗口本来就是直角，天然贴边）。
5. 把框抽成 `ui/window_frame.slint`（`win-w / win-h / rounded / line-color`），便于离屏像素回归；主界面引用它。

**代价**：+1 UI 文件、Rust 多一个返回值；弧的 viewbox 是一个"反 fit"的推导值（注释里必须写清楚，否则下一个人会把它「化简」掉）。

### 方案 C（不推荐）

关 DWM 圆角 + 透明窗口自绘整套外壳。控制力最强，但要改窗口透明/阴影/性能，现阶段不值得。

## 4. 验证

1. 最外行/列必须是线色（不是背景色）→ 锁"贴边"；

## 5. 落地结果（2026-10-18 02:00）

最终按「修正后的方案 B」实现，**方案 A 的对照改动已全部删除**：

| 文件 | 改动 |
|---|---|
| `ui/theme.slint` | `radius-win` 改为 `8px`（不再 `/ device-pixel-ratio`）；新增 `radius-win-px: 8.0` 供弧公式使用 |
| `ui/window_frame.slint`（新增） | `WindowFrame` 组件：直边贴边界 + 四角"反 fit viewbox"描边弧 + `rounded` 门控 |
| `ui/app.slint` | 删掉内联 `#win-edge-frame` 整块，改为 `WindowFrame` 实例；新增 `win-rounded` 属性；BrandLogoBtn/WinBtn 注释同步 8 DIP 事实 |
| `src/app/window.rs` | `apply_window_chrome` 返回 DWM 圆角 HRESULT（`corner_hr == 0`）；系统边框保持 `DWMWA_COLOR_NONE` |
| `src/app.rs` | 首 winit 事件把返回值写进 `set_win_rounded()`；托盘弹层调用忽略返回值 |
| `tests/window_frame_geometry.rs`（新增） | 离屏几何回归（DPR=1）：radius token、四边贴边/1 设备像素、四角弧加权半径、直角回落 |

### 5.1 离屏回归（`cargo test --test window_frame_geometry`）

- `radius-win` 在 DPR=1 / DPR=2 下都必须是 8 逻辑 px（旧实现 DPR=2 时 4 → 红）；
- 四边最外像素 == `border-strong`、第 2 像素 != 描边色（旧实现线在偏移 1）；
- 左下角弧墨迹 α 加权半径 ∈ [r−1.4, r−0.05]（≈r−0.5；旧实现 ≈5.7 → 红）；
- 其余三角有弧墨迹；`win-rounded=false` 时四角为描边色。

### 5.2 真机实测（200% DPI，1500×900 窗，`target/exp-edge/out/planb2-*`）

| 项 | 旧实现（before） | 新实现（planb2） |
|---|---|---|
| 四边最外像素 | 内容色（线在往里第 2 像素） | **`border-strong`（78,81,87）** |
| 边厚 | 线 1 设备像素 + 外侧 1 设备像素内容缝 | **1 设备像素，外缘即窗口边界** |
| 四角 | 45° 扫描无描边色像素（弧被 DWM 裁掉） | 弧连续，墨迹半径 ≈ r−0.5，紧贴裁剪弧 |
| 渲染器 | — | 软件渲染器（debug + release 默认）与 **femtovg**（`SLINT_BACKEND=winit-femtovg`）均验证：四边 5 个采样点全为 1 物理像素、最外像素 = border-strong、无第二圈线 |

- 四角 1 设备像素弧在 200% 下是 0.5 逻辑 px 的曲线，AA 会让局部亮度在 57~103 之间浮动（直边是满值 78）——这是"1 设备像素曲线"的固有表现，不是断线；`analyze.ps1` 的 45° 采样可复核（旧实现该处完全无描边色）。
- 角弧外缘与 DWM 裁剪 AA 叠加，最外 0.5 设备像素略被稀释；若日后觉得角部偏淡，可按 §6 的 ε 微调（本轮实测无需）。

## 6. 风险 / 回滚

- 纯视觉改动，不碰数据/交互/配置。
- 若某系统版本 DWM 半径与 8 DIP 不符：改 `Theme.radius-win-px`（同时同步 `ui/window_frame.slint` 里 commands 的 `8`）；四角异常时 `win_rounded=false` 可回退直角框。
- 角弧外缘的 AA 与 DWM 裁剪 AA 叠加，最外 0.5 设备像素略暗；若肉眼可辨，把 viewbox 公式里的 R 用 R+ε（ε≤0.25 物理像素）微调（本轮实测无需）。
- 回滚：还原 `ui/app.slint` 的 WindowFrame 实例为旧内联块、`theme.slint` 的 `radius-win`、`src/app/window.rs`/`app.rs` 的返回值改动，删除 `ui/window_frame.slint` 与测试文件。

## 7. 结论

- 方案 A（DWM 系统边框）对齐完美但 200% 下是 2 物理像素（1 DIP），与「1 设备像素」语言冲突 → **不采用**。
- 最终采用方案 B：几何上线外缘与窗口边界重合、四角贴合 8 DIP 裁剪弧、线宽 1 设备像素；离屏回归 + 真机像素双重验证。
- 遗留：`target/exp-edge/` 下的实验脚本/截图仅作证据保留，可随时删除；`Experiment` 临时开关已全部移除。
