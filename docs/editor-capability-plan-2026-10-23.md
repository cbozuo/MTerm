# MTerm 内置编辑器 · 能力上限与交互路线（决策稿）

> 2026-10-23 · 承接 `docs/design/editor-hifi-2026-10-23.html`（界面与交互）
> 与 `docs/design/editor-settings-hifi-2026-10-23.html`（编码 / 外观 / 格式化）。
> 本稿只回答三件事：**能打开多大的文件**、**交互还能怎么增强**、**对标 iShellPro 取什么舍什么**。

---

## 0. 结论摘要

1. **当前上限是硬拒绝**：512 KB / 20000 行 / 单行 64 KB，三道闸门任一触发就报错
   （`src/sftp/impls/sftp.rs:1710-1712`）。这不是"慢"，是"打不开"。
2. **改造后上限由「内存」决定，不再由「行数」决定**。Slint `ListView` 虚拟化让渲染成本
   与文件大小彻底解耦，`ropey` 让编辑成本变成 O(log n)。
3. **建议分级**：桌面可编辑 10 MB / 只读浏览 50 MB；Android 可编辑 2 MB / 只读浏览 10 MB。
   超出后走**已经存在**的「外部打开/编辑」通道。
4. **发现一个数据丢失风险**：保存时**没有任何远端冲突检测**（`src/app/sftp_callbacks.rs:850-866`
   直接 `write_text` 覆盖），而 `mtime` 明明拿得到（`sftp.rs:2161` 已在文件面板用）。
5. **最有差异化的交互是「编辑器 ↔ 终端联动」**——iShellPro 这类移动端 SSH 工具做不到，
   而 MTerm 同一会话里两者都在。

## 1. 现状基线（实测，非估算）

| 项 | 实测值 | 位置 |
|---|---|---|
| 文件大小上限 | **512 KB** | `src/sftp/impls/sftp.rs:1710` `MAX_BUILTIN_EDITOR_BYTES` |
| 行数上限 | **20 000 行** | `:1711` `MAX_BUILTIN_EDITOR_LINES` |
| 单行上限 | **64 KB** | `:1712` `MAX_BUILTIN_EDITOR_LINE_BYTES` |
| 读入方式 | SFTP `read_to_end` **一次性全量** | `:1805-1806` |
| 拒绝文案 | 「文件过大,无法在内置编辑器中打开(上限 512 KB),请使用外部打开/编辑或下载」 | `:1758-1760` |
| 行模型 | `content.split('\n')` → `Vec<SharedString>` | `src/app.rs:11952` |

| 渲染成本 | 每行 1 个隐藏 `TextInput` 测高 + 1 个行号 `Text` + 1 个容器 ≈ **3N 个 Slint 元素** | `ui/editor_window.slint:252-275` |

| 已有兜底 | 「外部打开/编辑」：下载到临时目录 → 交 OS 打开 → watcher 监听改动 → 回写 | `sftp.rs:1602-1610`、`:2053 spawn_edit_watcher` |

> ⚠️ 编辑器有**两份重复实现**：`ui/editor_window.slint:291`（独立窗口）与
> `ui/app.slint:5263`（主窗口内嵌）。所有改造必须同步两处，或先抽共享组件。

## 2. 文件大小上限：改造前后对照

### 2.1 约束链推导

| 环节 | 现状 | 改造后 | 说明 |
|---|---|---|---|
| 网络读入 | 1× bytes | 1× bytes | SFTP 协议决定，无法流式到 rope（除非改协议层） |
| 文本存储 | 1× String | **1.5–2×**（rope） | rope 节点有结构开销 |
| 行模型 | **1.3–2×**（N 个 String，每个 24 B 头 + 堆分配） | **0**（不建全量行模型，按需 `rope.lines()`） | 这是最容易省掉的一块 |
| **渲染** | **3N 个 Slint 元素** | **≈ 50 个（视口行数）** | ⭐ `ListView` 虚拟化，**与文件大小彻底解耦** |
| 语法高亮 | 无 | 增量（syntect `ParseState`），但多行语法状态需从行首累积 | 决定"带高亮"的档位更低 |
| 查找 | 同步全量扫描，阻塞 UI | 后台线程（tokio 已有），额外内存 O(1) | |

**峰值内存 ≈ (1 bytes + 1.5~2 rope) × 文件大小**，即约 **3×**。

### 2.2 分级上限（建议值）

| 档位 | 模式 | 能做什么 | 桌面 (Win/mac/Linux) | Android | 峰值内存 |
|---|---|---|---|---|---|
| **F1** | 只读浏览 | 滚动、查找、复制；**无高亮、无编辑** | **50 MB** | **10 MB** | ~150 MB / ~30 MB |
| **F2** | 可编辑，无高亮 | 编辑、保存、行尾/缩进规范化 | **10 MB** | **2 MB** | ~30 MB / ~6 MB |
| **F3** | 可编辑 + 语法高亮 | 完整编辑体验 | **4 MB** | **1 MB** | ~14 MB |
| **F4** | 超出全部档位 | → **走已有的「外部打开/编辑」** | 无限 | 无限 | 下载到本地 |

### 2.3 相对现状的收益

| | 现状 | 改造后（F3 桌面） | 倍数 |
|---|---|---|---|
| 能打开的文件 | 512 KB | 4 MB | **8×** |
| 能打开的文件（F2） | 512 KB | 10 MB | **20×** |
| 行数上限 | 20 000（硬拒） | **无独立上限**（渲染解耦） | ∞ |

### 2.4 落地上必须改的三处

| # | 位置 | 改法 |
|---|---|---|
| 1 | `sftp.rs:1710-1712` 三个常量 | 改为**分档阈值**；`LINES` 上限**直接删除**（虚拟化后无意义） |
| 2 | `sftp.rs:1795-1797` 读入前拦截 | 改为：超 F3 → 走 F1/F2；超 F4 → **提示走外部编辑**（别硬拒） |
| 3 | `sftp.rs:1804-1806` 一次性 `read_to_end` | 大文件改为 `take(limit)` 分块 + 直接喂 rope，**避免 bytes 与 rope 同时驻留** |

> ⚠️ 现有测试 `sftp.rs:2998 / :3007` 固化了三个上限的行为，**改阈值必须同步改测试**。

## 3. 交互增强路线图

按「MTerm 独有优势 × 实现成本」排序，不按功能数量。

### P0 · 编辑器 ↔ 终端联动（**MTerm 差异化最强**）

MTerm 的编辑器开在**同一个 SSH 会话**里，终端就在旁边。iShellPro 这类以移动端为主的工具做不到。

| 动作 | 交互 | 落地 |
|---|---|---|
| 执行当前行 | `Ctrl+Enter` | 取当前行文本 → 送到该会话的终端输入 → 回车 |
| 校验语法 | `Ctrl+Shift+Enter` | `bash -n <file>` / `python -m py_compile` → 结果回显 |
| 重载服务 | 命令面板 `:reload` | 预设 `systemctl reload nginx` 等模板 |
| 输出跳行 | 终端里识别到 `file.conf:42:` → 点击 → 编辑器跳到第 42 行 | 解析终端输出 |

**为什么排第一**：这是 MTerm 唯一能打赢 iShellPro / Termius / SecureCRT 的地方，且**不需要自研编辑内核**。

### P1 · 保存策略 + 冲突检测（**修数据丢失风险**）

> 🔴 **现状缺陷**：`src/app/sftp_callbacks.rs:850-866` 保存时直接 `h.write_text(path, content)`，
> **不做任何远端状态检查**。远端文件在你编辑期间被改过（别人改了 / 日志轮转替换 / 部署覆盖），
> MTerm 会**静默覆盖**。而 `mtime` 明明拿得到（`sftp.rs:2161` 已在文件面板显示修改时间）。

| 能力 | 交互 | 落地 |
|---|---|---|
| 打开时记录 `mtime` + `size` | 无感 | 存到编辑器状态 |
| 保存前比对 | 无感 | `sftp.metadata()` → 不一致则弹「远端已改动」 |
| 冲突处理 | 三选一 | **覆盖** / **放弃我的改动** / **另存为新文件** / **看 diff** |
| 保存前自动格式化 | 设置项 | 走第二稿的格式化面板 |
| 保存前 diff 确认 | 可选设置项 | 与远端当前内容对比 |

### P2 · 键盘命令集（Helix 式，第一稿已列）

`:` 命令面板 · `Ctrl+D` 选中下一处相同 · `Alt+↑/↓` 整行移动 · `Ctrl+G` 跳行 ·
`Ctrl+Shift+K` 删除行 · `Esc` 清多光标。
**这一档几乎不需要新依赖**，但需要 P1 之后的薄内核（selection/transaction 模型）。

### P3 · 移动端手势（Android 必做）

双指横滑 = 横向滚动 · 双指捏合 = 缩放字号 · 长按 = 选词/上下文菜单 · 硬件键盘快捷键。

### P4 · 多标签 + 文件变更检测

一个会话内开多个文件（tab）· 远端文件被改动的通知 · 拖文件进编辑器。

## 4. 对标 iShellPro

### 4.1 核实到的产品事实

> 来源：**二手**（转售站商品页 lizhi.shop / Apple Developer 页面转述），非官方文档，
> 未能访问官网原始页面，故功能清单仅作参考，不作为设计依据。

| 项 | 内容 |
|---|---|
| 定位 | 多平台 SSH 工具（Windows / macOS / Linux / iOS / Android） |
| 开发商 | Henan Tuyi Network Technology Co., Ltd（河南途易网络科技有限公司） |
| 编辑器 | **SFTP 文件编辑器，内建语法高亮 + 行号** |
| 其他 | SSH 连接管理、本地终端、SFTP 传输（文件夹上传下载 + 断点续传）、AI 辅助命令生成、自定义快捷键/主题/字体、命令模板、批量连接、加密云同步 + Markdown 笔记 |
| 定价 | 免费版 / Pro 订阅 |

### 4.2 结论：**它的编辑器范围 = MTerm 现在的目标形态**

iShellPro 的内置编辑器就是「SFTP 编辑 + 语法高亮 + 行号」——**和 MTerm 第二稿的目标基本重合**。
这说明两件事：

1. **MTerm 的定位选对了**：轻量 SSH 客户端 + 够用的内置编辑器，是有商业验证的方向。
2. **它不能作为「交互参考标杆」**：它是移动端优先的产品，桌面级键盘流和多标签不是它的强项，
   而 MTerm 有桌面 + 移动双端。

### 4.3 值得借鉴 / 不该照搬

| 借鉴 | 理由 |
|---|---|
| ✅ 语法高亮 + 行号作为 SFTP 编辑器的**基线** | 已验证的需求 |
| ✅ **自定义快捷键** | MTerm 现在没有统一键位表 |
| ✅ **命令模板**（`systemctl reload nginx` 这类预设） | 和 P0 的「编辑器 ↔ 终端联动」天然合流 |
| ❌ 不照搬 **AI 辅助** | MTerm 无 AI 集成，是独立方向的活，别混进编辑器改造 |
| ❌ 不照搬 **云同步 / Markdown 笔记** | 与编辑器性能无关，属于另一个产品线 |

## 6. 下一步建议

**先做 P0 三项**（零新依赖、1–2 天、可独立验收）：
① `ListView` 虚拟化 ② 字体 bug ③ **保存冲突检测**。
③ 是数据安全问题，优先级不低于性能。

**然后 P1 大文件分档**——它把「512 KB 打不开」变成「10 MB 可编辑 / 50 MB 可读」，
这是相对现状**最直观的用户价值**。

**P2 的编辑器 ↔ 终端联动**放在性能之后做——性能不达标时，其他交互都谈不上顺滑。
